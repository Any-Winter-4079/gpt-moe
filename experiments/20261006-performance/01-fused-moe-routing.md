# Experiment 01: fused MoE dispatch and combine

Baseline: `7704a680a84be3000e407887e149914215c655c5`. Apply `01-fused-moe-routing.patch` independently to that baseline. The production source has not been changed.

## Mechanism

The existing grouped expert GEMMs remain intact. Four routing kernels replace dispatch/combine and their autogenerated backwards:

- Dispatch gathers tokens directly into the expert computation dtype and constructs the inverse permutation in the same kernel.
- Dispatch backward gathers the selected expert gradients for each token and reduces them without atomic scatter-add.
- Combine gathers the sorted expert outputs, casts and weights them, and reduces top-k directly into the output.
- Combine backward writes each packed output-gradient row once and computes each gate gradient in the same kernel.

The intended benefit is reduced routing memory traffic and backward launch/atomic overhead. The custom combine backward saves the packed expert output in its computation dtype, rather than explicitly keeping the unpermuted output in the hidden-state dtype. At 4 × 8192 tokens, top-2, D=1024, those tensors are 128 MiB in BF16 versus 256 MiB in FP32 per layer. These are tensor sizes, **not measured compiled-memory savings**: Inductor can already fuse or rematerialize parts of the baseline. No speedup is claimed without GPU measurements. One CTA per token can also be inefficient for very small shapes or very large top-k.

## Scope and numerical behavior

Affected files: new helper `model/grouped_routing.py` (154 lines), plus the routing calls in `model/moe.py`. There is no added configuration switch, dependency, CPU production fallback, weight repacking change, or expert GEMM change.

All five activations, optional expert biases, top-k values, both gate-normalization modes and load-balance loss remain available. The activation cast before downprojection stays intact. Individual 2D expert parameters, state-dict names and optimizer input shapes stay intact. DDP and PP still use the same module interface and parameter objects; distributed execution itself requires GPU validation.

The kernels retain the original casts around gather, expert-output weighting, and gradient casts. FP32 is used for reductions. The forward combine disables FP contraction to preserve the separate multiply and add. Summation order can differ, particularly for top-k > 2 and BF16 hidden-state gradients, where the baseline scatter may round repeatedly. Expect normal floating-point differences, not bitwise equivalence. First-order training autograd is implemented, matching the existing grouped-linear path; higher-order derivatives are not added.

## Completed local checks

- Python syntax compilation of both affected files.
- Actual routing kernel bodies run through a CPU Tensor interpreter: 36 combinations of token/dimension shapes, top-k 1/2/8, FP32/BF16 input and packed dtypes, including non-contiguous inputs and upstream gradients. Forward values, permutations and all routing gradients matched PyTorch algebra within the stated dtype/reduction tolerances.
- CPU custom-op stand-ins passed `torch.library.opcheck` schema, autograd registration, fake-tensor and AOT dispatch checks.
- Synthetic MoE algebra checked all five activations, bias/full-softmax gating and top-k 1/2/8 against the original expert loop: output, auxiliary loss, input/router/expert gradients and parameter names/shapes passed.
- Fullgraph AOT forward/backward passed using the CPU stand-ins. The interpreter executes the kernel indexing and arithmetic but does **not** validate Triton GPU lowering, CUDA performance or Inductor CUDA code generation.
- `git apply --check` and whitespace checks on the delivered patch.

No training job, inference job, external GPU run or paid run was performed. CUDA compilation, numerical comparison on SM120, GPU memory use and performance are **unverified**.

## Rented-GPU comparison

Apply this patch alone. Use identical baseline weights, seed, input batches, token schedule, optimizer, precision, top-k and DDP/PP settings. First compare forward/auxiliary losses and input/router/expert gradients with identical upstream gradients, including the FP32-hidden/BF16-expert case; also exercise top-1, top-8 and a bias/SwiGLU case. Validate CUDA fullgraph compilation in both existing parallel modes.

Warm both versions separately at every scheduled batch shape and exclude compilation/autotuning from timings. Compare median steady-state step time, tokens/s, peak allocated memory, and routing forward/backward CUDA time. The strongest hypothesis is improvement in routing backward and saved-activation memory; a regression or negligible change means GEMMs or compiler fusion dominate. Keep this variant only if end-to-end measurements support it.
