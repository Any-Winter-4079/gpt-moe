# 05 — Batched Polar Express Muon updates

Baseline: `7704a680a84be3000e407887e149914215c655c5`. Candidate changes only `optimizers/muon.py`; production sources are unchanged. Apply independently with `git apply experiments/20261006-performance/05-batched-muon.patch`; reverse with `git apply -R` and the same path.

The current optimizer calls Polar Express separately for every matrix, although the existing backend and both Triton kernels already support independent 3D batches. This patch groups updates by shape, device and dtype within each parameter group, then orthogonalizes at most eight matrices per call. QKV projections still split into three independently normalized square matrices. Per-parameter momentum, in-place Nesterov gradient changes, `None` gradients, parameter objects/order, state dictionaries and learning-rate scaling are preserved. Existing SVD and Newton–Schulz functions and their per-matrix calls remain unchanged. No optimizer algorithm, coefficient, epsilon, iteration count or configuration changes.

With all gradients present, the configured eight-layer model has 64 up projections, 64 down projections, 32 attention projections and eight routers: 168 backend calls become 21. A four-layer pipeline stage changes from 84 to 11. The existing five PE iterations each issue three matrix-product kernels, so their corresponding source-level calls change from 2,520 to 315 for a full replica, or 1,260 to 165 per four-layer stage. These are call counts, not measured CUDA launch counts or speedups. Parameter-wise momentum and weight-update kernels remain. Buckets use only the local optimizer's parameters and distinguish devices; no rank count or single-GPU assumption is added.

For eight FP32 matrices of shape 1024×2048, the gradient stack occupies 64 MiB. Named PE BF16 X/C and square A/B buffers add approximately 96 MiB, giving a 160 MiB basic working set, compared with about 12 MiB of corresponding backend buffers for one matrix. A previous output view may retain another 32 MiB between chunks; normalization temporaries and compiler/library workspace add further memory. Actual CUDA peak allocation must be measured. The eight-matrix bound avoids stacking all 64 matrices in an orientation at once.

Local CPU checks used PyTorch 2.9.0 with compile decorators removed and CPU matrix-product substitutes for the two unchanged Triton kernels. They covered three batch sizes, tall/wide/square matrices, zero inputs, BF16/FP32 inputs with widely different per-matrix magnitudes, two parameter groups, mixed dtypes, noncontiguous gradients, QKV, changing missing gradients, five optimizer steps, both Nesterov settings and loading baseline optimizer state. Momentum buffers and mutated gradients were bitwise equal; optimizer weights were bitwise equal in these cases for all three backends. A separate PE component comparison observed a maximum absolute difference of 0.00390625 and aggregate relative L2 difference of 0.00035411 (0.0354%) between batched and individual CPU products. Batched MM is not promised bitwise identical. Syntax and patch applicability checks passed.

GPU gate: compare update errors for actual 1024×2048/2048×1024/1024×1024 matrices and QKV; warm up each bucket shape; then measure steady-state Muon time, total step time and peak memory on the original GPU configuration, including DDP and two-stage pipeline runs. Check actual Triton batch indexing, unchanged autotuning behavior and CUDA graph/compile behavior there. CPU reference checks do not validate those kernels or establish a speedup. Performance could regress if stack/copy cost or batched GEMM efficiency outweighs fewer launches.
