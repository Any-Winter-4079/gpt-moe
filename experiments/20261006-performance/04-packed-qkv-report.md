Baseline: `7704a680a84be3000e407887e149914215c655c5`. Research checked 2026-10-06.

`04-packed-qkv.patch` is an independent implementation experiment: execute Q/K/V projections with one `F.linear`, while retaining the existing `q_proj`, `k_proj`, and `v_proj` parameters. It changes only seven lines of `SelfAttention.forward` in `model/attention.py`. Apply it to the baseline by itself. GPU performance and training quality remain unmeasured.

The important distinction is retaining three registered matrices. Replacing them with one parameter would make Muon orthogonalize a different matrix and change optimization. Here, concatenation participates in autograd, gradients return to the original parameters, state-dict keys/shapes remain identical, and the split sizes follow each layer's actual Q/K/V widths. Biases remain supported. There is no feature flag or duplicate attention implementation.

For large token batches, one wider GEMM may read the input more efficiently than three separate GEMMs, and backward can calculate the input gradient with one GEMM instead of three plus additions. The local exported ATen forward graph contains two GEMMs including `c_proj`, versus four in the baseline. This is a structural observation, not a GPU speed estimate. Packing also costs a weight concatenation on every call: the default three 1024x1024 FP32 matrices contain 12 MiB per layer, before autocast. Larger GEMMs, weight packing, the resulting V strides, and CUDA compiler choices must be evaluated together. There is no claim that this patch will reduce the reported ~900 ms iteration time.

The candidate leaves the mask construction, FlexAttention and SDPA calls, score modifiers, RoPE placement and frequencies, QK normalization, gain clamping, local/global layer selection, and pipeline boundaries unchanged. MHA/GQA/MQA retain the baseline's current head mapping. The public `GPT.forward` currently normalizes a 2D token-validity mask; `SelfAttention` passes broadcastable 2D/3D/4D SDPA masks through to PyTorch. Both interfaces remain as they are. Absolute positional embeddings are implemented outside attention and are unaffected.

Local checks used macOS CPU PyTorch 2.9.0, not target PyTorch 2.10/CUDA 12.8/Triton 3.6. The baseline was read from a temporary archive; the candidate source was loaded in memory. Only the patch and this report were written to the repository.

- 540 SDPA forward/backward comparisons: 3 KV-head counts (1/2/4), RoPE/NoPE/absolute configuration, normalization off/RMS/L2, bias off/on, local/global attention widths, and FP32/FP64/BF16 autocast/all-BF16/no-autocast input casting. Widths were D=16, H=4, local attention=16 and global attention=32; batch=2, sequence=8. Masks cycled through none, boolean and additive 2D/3D/4D, and batch-broadcast 4D. Causal/noncausal configurations and noncontiguous input strides were exercised. Gains ranged from 0.4 through 6.0, including the clamp at 5.0. Seed: 8231.
- 24 additional FlexAttention CPU reference comparisons covered MHA/GQA/MQA, local/global width, softcap off/exact/rational/clamp, RMS/L2, and a per-head block mask combining causal, local-window, document-like, and invalid-token constraints. The CUDA PTX softcap lowering was not executable on this machine; it is untouched by the patch.
- Both versions passed full-graph `torch.compile(..., backend="aot_eager", fullgraph=True)` attention forward/backward checks. This does not validate CUDA Inductor kernels.
- State-dict keys and parameter names/shapes/dtypes were checked for equality in every comparison. `git apply --check` succeeded against the clean baseline. DDP/NCCL and pipeline execution were not run locally; their parameters and interfaces are unchanged.

The expected numerical change is in dX: the baseline separately computes three projection input gradients and adds them, whereas the packed projection performs one larger reduction. In BF16 this changes where rounding occurs. An initial checker mistakenly compared a noncontiguous baseline input with a contiguous candidate clone; its larger apparent BF16 output/parameter differences disappeared after matching strides. The table above uses corrected, matching strides.

Current upstream research and ranking:

1. **Packed QKV, delivered here.** The official modded-nanogpt head resolved to `4ea6b937337a4889b8cfe3f38a93d120048d8f71` (2026-09-28). Its attention uses packed QKV in training and concatenates QK/V weights for a single BF16 validation projection. The transferable idea is projection packing, without its FP8 cache, parameter banks, paired-head design, or attention changes. [Verified attention implementation](https://github.com/KellerJordan/modded-nanogpt/blob/4ea6b937337a4889b8cfe3f38a93d120048d8f71/track_1_short/model/attention.py#L176-L197).

2. **Fused QK normalization/RoPE, investigate after a GPU profile.** Upstream fuses normalization, rotation, and some backward quantization. Its kernel has fixed FP32 RMS math/epsilon, normalization before rotation, and paired-head/key-offset assumptions. This repository rotates before normalizing, supports RMS and L2 plus learned/clamped gains, and has arbitrary local/global dimensions. Copying upstream would change behavior. A custom kernel could preserve this repository's equations, but would need meaningful CUDA backward/precision testing and must beat the fusion already produced by Inductor. No untested custom kernel is delivered. [Verified fused kernel](https://github.com/KellerJordan/modded-nanogpt/blob/4ea6b937337a4889b8cfe3f38a93d120048d8f71/track_1_short/perf/kernels/qkv_rope.py#L1-L70).

3. **Native GQA, useful only for GQA/MQA configurations.** Avoiding expanded KV tensors is attractive, but the default configuration has 16 query and 16 KV heads, so it would not help this default. There is also a pre-existing mapping issue: expanded KV heads are grouped (for example `[k0,k0,k1,k1]`) while `k_scale.repeat` interleaves gains (`[s0,s1,s0,s1]`). Normalizing before native GQA with the seemingly natural per-KV scales would silently change that baseline behavior once scales diverge. The delivered patch preserves the current mapping. A correctness decision about that mismatch should be separate from performance work.

4. **FlashAttention-4 on SM120 is a possible future backend, not a substitute in this patch.** Official FlashAttention head `76d9331028192d06da018c034979765aa0f22899` (2026-10-06) contains explicit SM120 forward and backward paths. Therefore, a blanket claim that current FlashAttention cannot run on RTX PRO would be wrong. Its FA4 FP8 attention path is explicitly SM100-only. Arbitrary masks, score modifiers, installation/runtime compatibility, and numerical parity would still need a separate integration. [SM120 forward](https://github.com/Dao-AILab/flash-attention/blob/76d9331028192d06da018c034979765aa0f22899/flash_attn/cute/interface.py#L1750-L1773), [SM120 backward](https://github.com/Dao-AILab/flash-attention/blob/76d9331028192d06da018c034979765aa0f22899/flash_attn/cute/interface.py#L2858), [FP8 restriction](https://github.com/Dao-AILab/flash-attention/blob/76d9331028192d06da018c034979765aa0f22899/flash_attn/cute/interface.py#L924).

5. **Reject a direct copy of the speedrun attention backend.** Its pinned patched FA3 binary targets the Hopper stack and requires a CUDA 13 runtime; its model assumes causal varlen attention and B=1. It is not a drop-in replacement for this CUDA 12.8/SM120, batch>1, Flex/SDPA configuration. [Pinned FA3 loader and provenance](https://github.com/KellerJordan/modded-nanogpt/blob/4ea6b937337a4889b8cfe3f38a93d120048d8f71/track_1_short/model/attention.py#L21-L39), [official FA3 requirements](https://github.com/Dao-AILab/flash-attention/blob/76d9331028192d06da018c034979765aa0f22899/README.md#flashattention-3-beta-release).

6. **Do not count architectural or training-policy changes as implementation speedups.** The current speedrun includes altered attention widths, paired heads, extra embeddings, sampled softmax, auxiliary prediction objectives, and aggressive sequence/batch/update schedules. Those may improve time to its benchmark target but change the model, objective, or training work. CUDA graph capture, parameter-update batching, and data movement are more general systems ideas, but must respect this repository's changing batches/windows, gradient accumulation, DDP, and PP. Existing Muon and grouped MoE already cover important upstream-inspired territory. [Current upstream technique list](https://github.com/KellerJordan/modded-nanogpt/blob/4ea6b937337a4889b8cfe3f38a93d120048d8f71/README.md).

A compiler check also matters: PyTorch v2.10.0 at `449b1768410104d3ed79d3bcfe4ba1d65c7f22c0` has empty default pre-gradient fusion options, and its public `fuse_parallel_linear_pass` is a stub. This does not prove every compiled backend will retain all three GEMMs, but there is no reason to assume this source-level packing is automatically redundant. [Fusion defaults](https://github.com/pytorch/pytorch/blob/449b1768410104d3ed79d3bcfe4ba1d65c7f22c0/torch/_inductor/config.py#L319-L339), [parallel-linear pass](https://github.com/pytorch/pytorch/blob/449b1768410104d3ed79d3bcfe4ba1d65c7f22c0/torch/_inductor/fx_passes/pre_grad.py#L100-L101).

Byte latent modeling and a diffusion head belong to a separate architecture experiment. BLT groups bytes into patches with a local encoder, a larger latent transformer, and a local decoder; it changes both the data representation and the compute distribution, rather than simply swapping the tokenizer. [BLT paper](https://arxiv.org/abs/2412.09871). A diffusion language model usually trains a transformer to denoise corrupted/masked sequences over a different objective; a separate diffusion decoder still needs its own training objective and iterative sampling design. It is not a drop-in LM-head replacement that preserves this autoregressive cross-entropy comparison. [LLaDA paper](https://arxiv.org/abs/2502.09992). Byte-level and token-level loss values also need a common unit such as bits per byte before numerical comparison.
